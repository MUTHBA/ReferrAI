# ReferrAI — Task Breakdown

Tasks are organized by roadmap phase. Each task is independently completable. Dependencies are noted where ordering matters. Estimates are in developer-hours for a single developer.

---

## Phase 1 — Foundation

### INFRA-001 · Docker Compose setup
Set up `docker-compose.yml` with four services: `db` (postgres:16), `backend` (FastAPI), `frontend` (React dev server), `nginx`. Include a shared `.env` file and volume for Postgres data.
**Est:** 3h

### INFRA-002 · Backend project scaffold
Initialize FastAPI app with `app/main.py`, `app/core/config.py` (Pydantic Settings), `app/core/database.py` (async SQLAlchemy engine + session factory), and `requirements.txt`.
**Est:** 2h | **Depends on:** INFRA-001

### INFRA-003 · Frontend project scaffold
Create React app (Vite), configure React Router, set up Axios instance with base URL and JWT interceptor, create layout shells for Admin and Partner views.
**Est:** 3h | **Depends on:** INFRA-001

### DB-001 · SQLAlchemy models
Define all ORM models: `User`, `PartnerTier`, `Partner`, `ReferralLink`, `ReferralCode`, `ReferralClick`, `ReferralConversion`, `Commission`, `Wallet`, `Withdrawal`, `Transaction`, `Setting`, `AIScore`, `FraudFlag`, `DiscoveredPartner`, `AuditLog`. Use `Base = DeclarativeBase()`.
**Est:** 4h | **Depends on:** INFRA-002

### DB-002 · Initial Alembic migration
Configure Alembic, generate and review the autogenerated initial migration from DB-001 models. Verify all constraints, CHECK constraints, and indexes are present.
**Est:** 2h | **Depends on:** DB-001

### DB-003 · Seed migration
Write a data migration to insert: default `PartnerTier` (Bronze), all canonical `Setting` keys with default values.
**Est:** 1h | **Depends on:** DB-002

### AUTH-001 · User registration endpoint
`POST /api/v1/auth/register` — validate email uniqueness, hash password with bcrypt, create `User` row, create `Partner` + `Wallet` rows if role is `partner`.
**Est:** 3h | **Depends on:** DB-002

### AUTH-002 · Login & JWT issuance
`POST /api/v1/auth/login` — verify credentials, issue JWT with `sub`, `role`, `exp`. Return access token.
**Est:** 2h | **Depends on:** AUTH-001

### AUTH-003 · JWT middleware & RBAC dependencies
`get_current_user` dependency (decodes JWT, fetches user). `require_admin` and `require_partner` dependencies (check role, raise 403 if wrong).
**Est:** 2h | **Depends on:** AUTH-002

### AUTH-004 · Password reset
`POST /api/v1/auth/forgot-password` — generate reset token, log it (email sending is out of scope; log to stdout for demo). `POST /api/v1/auth/reset-password` — validate token, update password hash.
**Est:** 2h | **Depends on:** AUTH-003

### AUTH-005 · Frontend auth flow
Login page, registration page, auth context (store JWT in memory, refresh on reload), protected route wrapper. Admin and Partner route guards.
**Est:** 4h | **Depends on:** AUTH-002, INFRA-003

### SET-001 · Settings service & repository
`SettingRepository.get(key)`, `SettingRepository.set(key, value, user_id)`. `SettingService.get(key, default)` — returns default if key missing. `SettingService.set()` — calls repository and writes to `audit_logs`.
**Est:** 2h | **Depends on:** DB-002

### SET-002 · Settings admin API
`GET /api/v1/settings` — list all settings. `PUT /api/v1/settings/{key}` — update a setting. Both require `require_admin`.
**Est:** 2h | **Depends on:** SET-001, AUTH-003

### SET-003 · Settings admin UI
Admin settings page: table of key/value pairs, inline edit, save confirmation. Call `PUT /settings/{key}` on save.
**Est:** 3h | **Depends on:** SET-002, AUTH-005

## Phase 2a — Referral Management

### REF-001 · Referral link generation
`POST /api/v1/referrals/links` (partner) — generate slug (UUID short or partner-name-based), build full URL, generate QR code (use `qrcode` library, return base64 PNG), insert `ReferralLink`.
**Est:** 3h | **Depends on:** AUTH-003

### REF-002 · Referral code generation
`POST /api/v1/referrals/codes` (partner) — generate unique alphanumeric code, insert `ReferralCode`.
**Est:** 1h | **Depends on:** AUTH-003

### REF-003 · Click tracking endpoint
`GET /r/{slug}` (public, no auth) — look up `ReferralLink` by slug, insert `ReferralClick` (parse IP from request, parse User-Agent), redirect to `destination_url`. Handle deactivated links with 404.
**Est:** 2h | **Depends on:** REF-001

### REF-004 · Conversion recording endpoint
`POST /api/v1/referrals/conversions` — accept `{ referral_code | click_id, conversion_value }`. Run attribution logic (see REF-005). Insert `ReferralConversion`. Trigger commission calculation (Phase 2b). Trigger AI scoring as BackgroundTask (Phase 4).
**Est:** 3h | **Depends on:** REF-003

### REF-005 · Attribution service
`ReferralService.attribute_conversion(partner_id, referral_code | click_id)` — read `referral.attribution_model` and `referral.attribution_window_days` from settings. For `last_click`: find most recent click within window. For `first_click`: find oldest click within window. Return the attributed click or `None`.
**Est:** 3h | **Depends on:** SET-001, REF-003

### REF-006 · Partner referral management UI
Partner page: list own referral links and codes, generate new link/code button, QR code display modal, copy-to-clipboard for link and code.
**Est:** 4h | **Depends on:** REF-001, REF-002

## Phase 2b — Commission Management

### COM-001 · Commission calculation service
`CommissionService.calculate_for_conversion(conversion_id)` — load partner tier, read commission settings, calculate amount (percentage × conversion_value, or fixed amount, or tier override). Insert `Commission` record.
**Est:** 4h | **Depends on:** SET-001, DB-002

### COM-002 · Wallet credit service
`WalletService.credit(partner_id, amount, reference_id)` — update `wallet.balance`, `total_earned`. Insert `Transaction` record (positive amount, `balance_after` snapshot). All in one DB transaction.
**Est:** 3h | **Depends on:** DB-002

### COM-003 · Wire commission into conversion endpoint
After `ReferralConversion` is inserted in REF-004, call `CommissionService.calculate_for_conversion()` then `WalletService.credit()` in the same request transaction.
**Est:** 1h | **Depends on:** COM-001, COM-002, REF-004

## Phase 2c — Partner Management

### PRT-001 · Partner profile API
`GET /api/v1/partners/{id}` — admin can view any; partner can view own only. `PATCH /api/v1/partners/{id}` — admin can update status/tier; partner can update name/contact.
**Est:** 3h | **Depends on:** AUTH-003

### PRT-002 · Partner tier CRUD API
`GET/POST/PATCH/DELETE /api/v1/tiers` — admin only. Validate `rank_order` uniqueness.
**Est:** 2h | **Depends on:** AUTH-003

### PRT-003 · Automatic tier upgrade
`PartnerService.evaluate_tier_upgrade(partner_id)` — called after COM-002. Compare partner's `total_referral_count` and `total_revenue_contribution` against all tier thresholds ordered by `rank_order` descending. Assign highest qualifying tier. Only upgrade, never downgrade.
**Est:** 3h | **Depends on:** COM-002, PRT-002

### PRT-004 · Partner list & profile UI (admin)
Admin partners page: sortable/filterable table of all partners with tier, status, referral count, revenue. Partner detail page: profile info, performance stats, AI score cards (placeholder), referral history.
**Est:** 5h | **Depends on:** PRT-001

### PRT-005 · Partner profile UI (partner)
Partner's own profile page: display name, tier, tier progress bar (progress toward next tier thresholds), performance stats.
**Est:** 3h | **Depends on:** PRT-001

## Phase 2d — Wallet & Payout

### WAL-001 · Wallet & balance API
`GET /api/v1/wallet` (partner: own wallet). `GET /api/v1/wallet/transactions` (partner: own transaction history, paginated).
**Est:** 2h | **Depends on:** AUTH-003

### WAL-002 · Withdrawal request endpoint
`POST /api/v1/withdrawals` (partner) — validate `amount > min_withdrawal_amount`, validate `amount <= wallet.balance`. Check for active fraud flags. Compare to `auto_approval_threshold`. If auto-approve: call `WalletService.debit()`, set status `approved`. Else: set status `pending`.
**Est:** 4h | **Depends on:** WAL-001, SET-001

### WAL-003 · Wallet debit service
`WalletService.debit(partner_id, amount, reference_id)` — update `wallet.balance`, `total_withdrawn`. Insert `Transaction` (negative amount). Raise if balance would go negative.
**Est:** 2h | **Depends on:** COM-002

### WAL-004 · Admin withdrawal review API
`GET /api/v1/withdrawals?status=pending` (admin). `PATCH /api/v1/withdrawals/{id}` — set status to `approved` or `rejected`. On approve: call `WalletService.debit()`. Write to `audit_logs`.
**Est:** 3h | **Depends on:** WAL-002, SET-001

### WAL-005 · Wallet & payout UI (partner)
Partner wallet page: balance, total earned, total withdrawn. Transaction history table. Withdrawal request form with amount validation.
**Est:** 4h | **Depends on:** WAL-001, WAL-002

### WAL-006 · Admin payout review UI
Admin payouts page: table of pending withdrawals (partner name, amount, requested date). Approve/reject buttons. Payout history tab.
**Est:** 3h | **Depends on:** WAL-004

## Phase 4a — Synthetic Data Generation

`SyntheticDataGenerator` class in `backend/app/ai/generators/`. Methods: `generate_partners(n)`, `generate_clicks(partner_ids, n)`, `generate_conversions(click_ids, n)`, `generate_fraud_labelled(click_ids, fraud_ratio)`, `generate_churn_labelled(partner_ids, churn_ratio)`. Use Faker for names/emails/IPs. All records tagged `is_synthetic=True`.
**Est:** 6h | **Depends on:** DB-002

### AI-DATA-002 · Synthetic data generation API
`POST /api/v1/admin/synthetic-data` (admin) — accept count parameters, call generator, bulk-insert records. Return counts of inserted records.
**Est:** 2h | **Depends on:** AI-DATA-001

## Phase 4b — Referral Quality Scoring

### AI-QUAL-001 · Quality scorer model
`ReferralQualityScorer` in `backend/app/ai/scoring/quality.py`. Train a Random Forest classifier on synthetic conversion data. Features: time-to-convert (minutes), source type, device category, conversion value (normalized), partner tier rank. Output: probability score × 100. Save model to disk with `joblib`.
**Est:** 5h | **Depends on:** AI-DATA-001

### AI-QUAL-002 · Quality score service
`AIService.score_referral_quality(conversion_id)` — extract features from DB, call `ReferralQualityScorer.predict()`, wrap in try/except, store result in `ai_scores`. Call `Explainer.explain()` and store explanation.
**Est:** 3h | **Depends on:** AI-QUAL-001

### AI-QUAL-003 · Wire quality scoring into conversion flow
In REF-004's `BackgroundTasks`, add `ai_service.score_referral_quality(conversion_id)`.
**Est:** 1h | **Depends on:** AI-QUAL-002, REF-004

### AI-QUAL-004 · Quality score display in UI
Referral detail: score badge with explanation tooltip. Partner profile: aggregate quality score. Partner dashboard: quality score card.
**Est:** 3h | **Depends on:** AI-QUAL-002

## Phase 4c — Fraud Detection

### AI-FRD-001 · Rule-based fraud pre-checks
`FraudRuleEngine.check(click_id)` — stateless, synchronous checks: (1) clicks > N per hour from same IP, (2) same device hash on > M different partners, (3) referral of own account (same user). Returns list of triggered rules. Reads thresholds from settings.
**Est:** 4h | **Depends on:** SET-001, DB-002

### AI-FRD-002 · Isolation Forest fraud detector
`FraudDetector` in `backend/app/ai/scoring/fraud.py`. Train Isolation Forest on synthetic fraud-labelled click pattern features: clicks_per_hour, unique_ips_per_partner, device_reuse_count, time_between_clicks. Normalize anomaly score to 0–100. Save model to disk.
**Est:** 5h | **Depends on:** AI-DATA-001

### AI-FRD-003 · Fraud scoring service
`AIService.score_fraud(click_id)` — run rule engine checks + Isolation Forest, combine into composite score, store in `ai_scores` (`score_type='fraud_risk'`), call Explainer. If score > `fraud.alert_threshold`: create `FraudFlag` record.
**Est:** 4h | **Depends on:** AI-FRD-001, AI-FRD-002

### AI-FRD-004 · Wire fraud scoring into click flow
In REF-003 (click tracking), add `BackgroundTasks.add_task(ai_service.score_fraud, click_id)`.
**Est:** 1h | **Depends on:** AI-FRD-003, REF-003

### AI-FRD-005 · Fraud alert review API
`GET /api/v1/fraud-flags?status=pending_review` (admin). `PATCH /api/v1/fraud-flags/{id}` — set `confirmed` or `dismissed`, write audit log.
**Est:** 2h | **Depends on:** AI-FRD-003

### AI-FRD-006 · Wire fraud gate into withdrawal
Update WAL-002: query `FraudFlag` for active partner flags before auto-approval decision.
**Est:** 1h | **Depends on:** AI-FRD-003, WAL-002

### AI-FRD-007 · Fraud UI
Admin fraud alerts page: list of pending flags with partner name, score, explanation, triggered rules. Confirm/Dismiss action. Fraud alert count on admin dashboard.
**Est:** 4h | **Depends on:** AI-FRD-005

## Phase 4d — Partner Churn Prediction

### AI-CHURN-001 · Churn predictor model
`ChurnPredictor` in `backend/app/ai/scoring/churn.py`. Gradient Boosting classifier on synthetic churn-labelled partner history. Features: days_since_last_referral, referral_count_30d, referral_count_90d, commission_trend (90d vs prior 90d), tier_rank. Output: churn probability × 100. Save model to disk.
**Est:** 5h | **Depends on:** AI-DATA-001

### AI-CHURN-002 · Churn scoring service
`AIService.score_churn(partner_id)` — extract features, call predictor, store in `ai_scores` (`score_type='churn_risk'`), call Explainer.
**Est:** 3h | **Depends on:** AI-CHURN-001

### AI-CHURN-003 · Scheduled churn scoring
`POST /api/v1/admin/run-churn-scoring` (admin trigger) — iterate all active non-synthetic partners, call `AIService.score_churn()` for each.
**Est:** 2h | **Depends on:** AI-CHURN-002

### AI-CHURN-004 · Churn score display in UI
Partner profile: churn risk score card with explanation. Admin dashboard: at-risk partners list (score > threshold). Admin partners table: churn risk column.
**Est:** 3h | **Depends on:** AI-CHURN-002

**Est:** 4h | **Depends on:** AI-QUAL-002, AI-CHURN-002, SET-001

### AI-RANK-002 · Ranked partner list API

### AI-RANK-003 · Ranking UI

**Est:** 2h | **Depends on:** AI-RANK-002

## Phase 4f — AI Partner Discovery

### AI-DISC-001 · Partner discovery model
`PartnerDiscovery` in `backend/app/ai/discovery/`. Load `all-MiniLM-L6-v2` Sentence Transformer. Embed each existing partner's `business_name + category`. For a candidate record, embed its description, compute cosine similarity to all existing partner embeddings. Score also factors `category_match` (exact = 1.0, related = 0.5) and `geographic_score` (same city = 1.0, same country = 0.5). Weighted average → `partner_potential` 0–100.
**Est:** 6h | **Depends on:** DB-002

### AI-DISC-002 · Discovery ingestion API
`POST /api/v1/admin/discovery/candidates` — accept CSV upload or JSON array of candidate records. Run `PartnerDiscovery.score()` for each. Insert `DiscoveredPartner` records.
**Est:** 3h | **Depends on:** AI-DISC-001

### AI-DISC-003 · Discovery UI
Admin partner discovery page: upload candidates (CSV), ranked results table with potential score and score factors, status actions (invite / dismiss).
**Est:** 4h | **Depends on:** AI-DISC-002

## Phase 4g — Explainable AI

### AI-XAI-001 · SHAP explainer
`Explainer` in `backend/app/ai/explainability/`. `explain_tree(model, features, feature_names)` — run SHAP TreeExplainer, return top 3 features by absolute value. `to_plain_language(score_type, top_factors)` — template-based strings per score type (e.g. "High referral velocity from a single IP contributed to this fraud risk score.").
**Est:** 5h | **Depends on:** AI-QUAL-001, AI-FRD-002, AI-CHURN-001

### AI-XAI-002 · Attach explanations to all scores
Ensure every call to `AIService.score_*()` passes through `Explainer` and stores `contributing_factors` (SHAP values dict) and `explanation` (plain text) in `ai_scores`.
**Est:** 2h | **Depends on:** AI-XAI-001

### AI-XAI-003 · Explanation display in UI
Anywhere a score is displayed (quality, fraud, churn, rank, potential): add an info icon that opens a tooltip or modal showing the plain-language explanation and top 3 contributing factors.
**Est:** 3h | **Depends on:** AI-XAI-002

## Phase 5 — Hardening & Demo Preparation

### TST-001 · Core API integration tests
Pytest tests for: register + login, create referral link, simulate click, record conversion, verify commission credited, verify wallet balance, test withdrawal auto-approval, test withdrawal blocked by fraud flag.
**Est:** 6h | **Depends on:** Phase 2 complete

### TST-002 · Graceful degradation test
Test that conversion recording and commission calculation complete successfully when all AI service methods raise exceptions. Verify `ai_scores` row has null score, no uncaught exception propagates.
**Est:** 2h | **Depends on:** Phase 4 complete

### TST-003 · Performance validation
Benchmark: standard API endpoints < 2s under light load. Scoring endpoints < 1s with pre-loaded models. Profile and optimize the slowest queries.
**Est:** 4h | **Depends on:** Phase 4 complete

### DEMO-001 · Demo seed script
Script that runs the full demo flow via API calls: create admin, create partner, generate referral link, simulate 10 clicks, record 5 conversions, generate synthetic data, run churn scoring, trigger discovery with sample candidates. Leaves the DB in a compelling state for demonstration.
**Est:** 3h | **Depends on:** Phase 4 complete

### DEMO-002 · Docker production config
`docker-compose.prod.yml` with nginx serving React build as static, environment variable validation, Postgres persistent volume, health checks.
**Est:** 2h | **Depends on:** INFRA-001
